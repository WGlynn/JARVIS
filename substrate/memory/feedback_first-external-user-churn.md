When we deliver something to the first external user of a system/artifact, expect scope and framing to churn 2-3 times before the deliverable crystallizes.

**Example (2026-04-15, Vedant + EDITH → JARVIS)**:
- Streamlined EDITH.md (92 lines) → fleshed EDITH.md (397 lines) → augmentation memo for Vedant's v3 spec (146 lines) → full JARVIS.md replacement (486 lines)
- Four versions in ~90 minutes. Each iteration was pressure-tested against a different framing (generic template → operational handbook → Vedant-specific bridge → full personal system).
- The final JARVIS.md is tighter than any of the EDITH drafts would have been because the framing got compressed three times.
- Will named it directly: "just the pressure of helping our first user."

**Why**: First-user delivery has a unique dynamic. The builder hasn't yet seen how the artifact survives contact with a stranger. Naming, scoping, and voice all get re-tested under that pressure. Over-optimizing for alignment before the first iteration wastes the churn that produces the final shape.

**How to apply**:
- When a new external user enters the picture, budget for 2-3 iterations before the deliverable stabilizes
- Don't insist on up-front alignment as hard — iterate cheaply and visibly
- Don't treat scope changes as failures; treat them as signal
- Do the cheap-to-reverse version first (local draft), the expensive version (public push) after the scope settles — but if Will says push anyway, push
- Don't apologize for the user's churn — it's upstream of the work, not a problem the work created
- When the pattern repeats (2nd, 3rd external user), reference this memory and move faster through the churn

**Inverse**: if a first-external-user deliverable goes through zero churn, be suspicious. Either the user hasn't actually stress-tested the artifact, or the deliverable is too generic to provoke a reaction.
