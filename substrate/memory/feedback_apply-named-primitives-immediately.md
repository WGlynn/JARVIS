# Apply a named primitive the turn after it's named

**Rule**: When Will names a primitive at end of session N, session N+1 must use it as the frame for work, not just load it into memory and then proceed as if it were background.

**Why**: The purpose of naming a primitive at reboot-point is to amplify the pattern in the next session. If it's just referenced but not USED to shape choices, the loop breaks — it becomes documentation rather than a mechanism. Will explicitly flagged this: when he said "keep making more documents like we just were" the correct frame was "keep making docs that run the Code↔Text Inspiration Loop" — pick docs that either (a) surface future-work hooks that will become code cycles, or (b) make existing code more pedagogically legible so its refinement edges show. Not: "pick random topics from whatever comes to mind."

**How to apply**:
- First turn of session N+1 after a primitive is named: cite the primitive BY NAME in my opening action.
- Let the primitive's rules constrain choices. If the loop primitive says "pick a doc's future-work item → ship code → update doc," then that IS what "keep going" means.
- When Will gives a directive that could fit multiple frames, the MOST RECENT primitive is the strongest frame.
- Test: before I take action, ask "does this action express the named primitive, or am I acting in a generic mode that ignores it?" If generic, stop and reframe.

**Connection to pattern-match drift on novelty**: A freshly-named primitive IS novel. If I pattern-match it to "just another memory entry," I've drifted. The naming is the signal that this one is load-bearing NOW.
